## 1. 공고 분석을 만든 방법과 화면·명세 문구 맞추기 (H3-r1-01)

**왜 남겼나**: 화면은 공고 분석을 AI가 했다고 말한다. 로딩 제목 "AI가 분석한 공고를 펼치고 있어요", ① 안내 "AI가 이 공고에서 면접 때 확인할 곳을 미리 찾아 두었어요", "AI 분석 요약", "AI가 찾은 확인할 점"이 그렇다. 그런데 `docs/API-SPEC.md` 부록 B는 지금 7건(K-MOCK-0001~0007)을 "사람이 이 모양으로 쓴 것"이라고 적었다. 실제로는 개발 중에 AI(Claude)가 만들고 팀이 고친 것이고, AI 파이프라인 담당(형원)의 파이프라인으로 만든 것은 아니다. 세진은 2026-10-27에 "AI 파이프라인이 적용되면 그때 고친다"고 정했다.

**AI 파이프라인을 붙일 때 할 일**

1. 공고 7건의 분석(`data/analysis/K-MOCK-000N.json`)을 파이프라인으로 다시 만든다. 파일에 만든 방법(파이프라인 이름·모델)과 날짜를 남긴다.
   - 진행: 다시 만들기 스크립트 `npm run analysis:regen`(후보 → 비교 보고서 → 사람이 `--apply`)까지 만들었다. 실제 엔노이아로 7건을 돌려 적용하는 것은 4.5단계다.
2. `npm run test:unit`의 분석 JSON 시험(근거 인용이 원문과 글자 그대로 같은지)과 질문 순서 시험(API-01·S4-13)을 통과시킨다. 순서가 바뀌면 ACCEPTANCE 예시 값을 같이 고친다.
3. `docs/API-SPEC.md` 부록 B와 「결정이 필요한 항목」 ?3을 실제로 만든 방법대로 고친다. 볼트 사본(`askback24 AI API 명세`)과 온보딩 문서 「공고 분석 7건은 손으로 쓴 것」 문장도 맞춘다.
4. /about-ai 「데이터 출처」 표에 "공고 분석 7건" 줄(만든 방법·검수)을 더한다.
5. 화면 문구(로딩 제목 LD-01, ① 안내, "AI 분석 요약")가 사실과 맞는지 다시 읽는다. 파이프라인으로 만들었으면 그대로 둔다.

**그 전까지**: 심사위원이 물으면 "시연 7건은 개발 중 AI로 미리 분석하고 팀이 검수했고, 실제 서비스에서는 AI 파이프라인이 공고마다 한 번 분석해 저장한다"고 답한다(/about-ai "고용24에 붙이면"과 같은 말).

## 2. 면접이 한 번인 공고의 처우 질문 (H3-r2-03 (가))

지금은 면접이 한 번인 공고에서 1차 ③ 아래 상자 글만 사실대로 바꿨다(HD-03). 처우 질문은 여전히 "면접 다녀왔어요" 뒤 최종 ③에서만 나온다. 2차 심사 뒤 기획안과 함께, 면접이 한 번인 공고는 1차 결과 아래에 처우 확인 2~3개(`final.backend.json` 처우 틀 그대로)를 주는지 정한다. 이렇게 하면 D-012(단계형)와 S4-15("1차 결과 화면에는 처우 질문이 없다")가 바뀐다.

## 3. 겹치는 카드 쌍 거르기 (H3-r2-01 (가))

지금은 신규 API 개발 "걱정돼요" 질문 틀만 바꿔 같은 비중 질문이 두 번 나오지 않게 했다(HD-01). 실제 AI를 붙여 문장이 자유로워지면, 겹치는 카드 쌍 표를 두고 규칙(`shared/rules.ts`)에서 뒤 카드를 대체 틀이나 6위 카드로 바꾸는지 다시 본다. 순서 시험(API-01·S4-13)을 함께 본다.

## 4. 회사 신호 시연 매핑 팀 확인 (D-318~D-321)

**왜 남겼나**: 시연 공고 7건의 가상 회사에 실제 회사의 공공데이터(국민연금·강소기업)를 붙여 보이기로 했다. 매핑은 `.env`의 `REAL_COMPANY_MAP`에만 둔다. 저장·화면에는 구간·방향만 쓴다. 그래도 이 방식은 CLAUDE.md "실제 사람·회사 정보를 넣지 않는다"와 ACCEPTANCE DATA-04("강소기업 여부는 '모의' 그대로")에 닿는다.

**할 일**

1. 세진께 확인을 받는다. 확인할 것: 매핑은 `.env`에만, 저장·화면은 구간·방향만, `caveat` 문구(D-320).
2. 확인되면 CLAUDE.md 「개인정보 금지」에 예외 한 줄을 더한다: "회사 신호 시연 매핑은 `.env`에만, 저장·화면에는 구간·방향만(D-318)".
3. SPEC-ISSUES DATA-04 판정에 따라 ACCEPTANCE와 e2e(시험 작성자)를 고친다.
4. 공고마다 업종(중분류)·규모·시도가 비슷한 실제 회사를 골라 `.env`의 `REAL_COMPANY_MAP`을 채운다(`.env.example` 형식). 스크립트 경고를 확인한다.

**그 전까지**: 매핑 코드는 만들되 `REAL_COMPANY_MAP`은 비워 둔다. 그러면 모든 공고가 시연 모의 값을 쓰고, 지금 화면·시험과 같다.
