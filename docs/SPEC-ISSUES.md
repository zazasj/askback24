# SPEC-ISSUES — 시험과 수용 기준이 어긋난다고 본 것

> 형식: `ID · 이유 · 제안 · 적은 에이전트`. 개발자는 e2e/를 고치지 않고 여기에 적는다. QA가 판정하고, 시험 쪽이 틀렸으면 수정 개발자가 고친다.

- API-05(e2e `quality.spec.ts` "API-05 화면 쪽") · PLAN은 API-05를 M3 범위로 두는데, 시험이 `makeFinalQuestions`(R-04 "1차 면접 다녀온 것으로 채우기"·"최종 질문 만들기", M5)를 거쳐서 M3만으로는 통과할 수 없다(시연 도구 버튼을 기다리다 시간 초과). 시험이 보는 내용(콘솔 로그에 경험 한 줄·들은 답 원문 없음)은 ACCEPTANCE와 맞다 · M3 판정은 단위 시험(`api/questions.test.ts`)으로 하고 e2e API-05는 M5 뒤에 판정. 또는 1차 흐름(`makeFirstQuestions`)만 거치는 경험 한 줄 로그 검사를 따로 나누기 · Claude(M3) · 판정: 해소, 바꿀 것 없음(2차 QA r1). M5가 끝나 e2e API-05가 두 폭에서 통과한다
- API-05(ACCEPTANCE 문구) · "응답 어디에도 … 경험 한 줄 원문이 없다"를 글자 그대로 읽으면 S4-13(5번 질문에 "FastAPI"·"경험 포함")과 부딪힌다. 검수 문장은 카드 질문 틀의 `{anchor}`에 경험을 그대로 붙이므로(데이터 `anchor_rule`) 대체 결과에는 경험 원문이 들어간다 · 문구를 "응답에 요청 값(경험 한 줄·들은 답)을 되돌려 주는 필드가 없고, 로그에는 없다"로 고치기. 지금 구현은 이 해석(D-043) · Claude(M3) · 판정: 문구 수정 수용(QA r1)
- R-04(e2e `s4-prep.spec.ts`) · 들은 답과 카드의 짝을 고객사 상주 질문만 보고, 나머지 세 답은 "구체적이었어요"인지만, 못 물은 질문은 이유만 봐서 ACCEPTANCE보다 약했다 · 행마다 "들은 답 → 카드 이름"(기존 시스템 유지보수·서비스 구조 설계·신규 API 개발)과 못 물은 행의 "DB 테이블 설계"를 확인하도록 강화 · QA r2 · 판정: 시험 수정(r2, 강화)
- G-03(e2e `global.spec.ts`) · ACCEPTANCE G-03에는 폭 제한이 없는데 휴대폰에서 건너뛰었다. 휴대폰 주 메뉴는 가로로 미는 한 줄로 정해졌다(D-026·D-071) · 건너뛰기를 지우고 두 폭에서 돌림. 화면 밖 항목은 `scrollIntoViewIfNeeded` 뒤에 누름 · QA r2 · 판정: 시험 수정(r2)
- S4-11(e2e `s4-prep.spec.ts`) · ACCEPTANCE는 칩을 누르면 입력칸이 "그 경험 문장"으로 채워진다고 하는데, 시험은 값이 비어 있지 않은지와 칩 3개 값이 서로 다른지만 봐서 엉뚱한 칩의 문장이 들어가도 통과했다 · 칩마다 누른 뒤 입력값이 `data/persona.json` `experience_chips`에서 label이 칩 글자와 같은 항목의 text와 같은지 확인(도우미 `resumeChips`) · QA r3 · 판정: 시험 수정(r3, 강화)
- S4-01·S1-05(e2e `s4-prep.spec.ts`·`s1-applications.spec.ts`) · ACCEPTANCE에 폭 제한이 없는데 휴대폰에서는 채용제목 확인을 건너뛰었다(도우미가 표 칸만 읽음) · `applicationPostingTitle`이 표가 없으면 휴대폰 카드 글에서 회사명 줄과 칸(지원일·열람일·지원결과·면접 준비)을 뺀 첫 줄을 읽고, 두 시험이 두 폭에서 S4 머리의 채용제목을 확인 · QA r3 · 판정: 시험 수정(r3)
- S1-09·S1-03·S3-04(e2e `s1-applications.spec.ts`·`s3-jobs.spec.ts`) · 휴대폰 카드에도 "지원일"·"지원결과" 칸 이름과 값이 보이는데, S1-09(두 시험)는 휴대폰을 건너뛰고 S1-03 3행·S3-04의 지원결과 "-"는 휴대폰에서 확인하지 않았다 · 도우미 `entryField`로 카드 글의 칸 값을 읽어 휴대폰 분기를 더하고 S1-09의 건너뛰기를 지움. S1-02(열 이름)는 표가 없어 건너뛰기 유지 · QA r3 · 판정: 시험 수정(r3)
- G-03(e2e `global.spec.ts`) · ACCEPTANCE 2차 「바뀌는 기존 항목」은 G-03을 그대로 두고(흐린 메뉴도 누르면 알림), G-14는 같은 주 메뉴 항목에 `aria-disabled="true"`를 요구한다. 그런데 G-03 시험은 흐린 항목을 `force` 없이 `click()`한다. Playwright(1.64)는 `aria-disabled="true"`인 button·link를 비활성으로 보고 click 전에 enabled를 기다려 10초 뒤 시간 초과("element is not enabled", 데스크톱·휴대폰 모두 실측). G-14(`demo-scope.spec.ts`)는 같은 이유로 `click({ force: true })`를 쓴다. 구현은 누르면 알림이 뜨고 주소가 그대로다(G-14 주 메뉴 시험과 `review/tmp/n1-scope.spec.ts`가 force 클릭으로 확인) · G-03의 흐린 메뉴 클릭을 `click({ force: true })`(또는 `dispatchEvent('click')`)로 바꾸고, 그 앞에 `aria-disabled="true"` 확인을 더하기. "채용정보" 클릭은 그대로 · Claude(N1) · 판정: 시험 수정 수용(2차 QA r1). 같은 흐름을 `aria-disabled="true"` 확인 + `click({ force: true })`로 다시 돌려 보니 두 폭 모두 네 항목이 알림을 띄우고 주소가 그대로였고 "채용정보"는 /jobs로 갔다(`review/tmp/qa-r1.spec.ts`, 커밋 안 함). 구현 문제가 아니다 · 시험 수정함(2차 r1, D-145)
