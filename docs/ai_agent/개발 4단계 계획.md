# 개발 4단계 계획 — ⓪ 업무 카드 초안

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Python AI 서버에 ⓪ `POST /api/ai/v1/card-drafts`를 연다.
- 직무 하나의 NCS 세분류 코드를 받는다.
- 규칙이 능력단위마다 카드 후보를 만든다.
- LLM이 후보를 묶고 카드 글을 쓴다.
- 결과는 `CardDef` 모양의 업무 카드 사전 **초안**이다. 저장하지 않고, 사람이 검수해 `data/cards.<직무>.json`으로 커밋한다.

**Architecture:**
- 그래프는 §9-5를 따른다: `fetch` → `candidates` → `group_and_write` → `check` → (`rewrite_cards`) → `finish`.
- 자료 출처는 네 가지다: NCS 정보_GW, 직무정보(215L01), 직업정보(212D01), 공통코드(21L01).
- 출처마다 **실제 클라이언트**를 만들어 가짜 응답으로 시험한다. 실행할 때는 키가 없으면 대체 자료를 쓴다(D-344).
  - 직무정보·직업정보·공통코드: `data/real/`의 실제 스냅숏(예전에 실제 키로 받은 값)
  - NCS 정보_GW: `data/mock/ncs-gw/<세분류>.json` 모의 응답
- 응답 `meta.sources`에 출처마다 `실제`·`실제 스냅숏`·`모의`를 적는다.
- 오프라인으로 돌리는 CLI(`npm run cards:draft`)도 둔다. 함수 한도 60초에 묶이지 않고, 결과를 `review/card-drafts/`(git 밖)에 쓴다.

**Tech Stack:** Python 3.12 · uv · FastAPI · LangGraph · httpx · pydantic 2 · pytest

**Spec:** `docs/ai_agent/에이전트 설계 확정.md` §2 ⓪, §3(⓪ 열), §6, §9-5 · 호출 형식 `docs/AI-API-명세서.md` 4번 · `shared/contract.ts` `CardDef`·`CardBook` · D-344 · 3단계 계획(같은 틀: 실제 클라이언트 + 가짜 응답 시험)

**범위 밖:**
- 새 직무 사전을 실제로 커밋하는 일. 초안 검수는 사람 몫이다.
- 화면 변경
- TS가 ⓪을 부르는 길
- 근무 방식(`kind: context`) 카드. 사람이 더한다.
- NCS 정보_GW의 실제 주소·필드 확인(4.5단계). 공개 페이지(data.go.kr 15157547)에는 형식이 XML이라는 것만 있고, 주소·동작·필드 이름은 활용신청 뒤 swagger에서 볼 수 있다.

## Global Constraints

- 1~3단계 Global Constraints를 그대로 따른다.
  - 키는 `os.environ`만 쓴다. 로그에 글을 남기지 않는다.
  - `e2e/`·CLAUDE.md는 고치지 않는다.
  - 커밋 형식과 Co-Authored-By를 지킨다. 경로를 적어 add 한다. push 하지 않는다.
  - DECISIONS는 한 줄씩, 다음 빈 번호부터 쓴다.
- 키: `DATA_GO_KR_KEY`(NCS 정보_GW), `WORK24_KEY_DUTY`(215L01), `WORK24_KEY_JOB`(212D01), `WORK24_KEY_COMMONCODE`(21L01)
  - 고용24 호출 모양은 `scripts/fetch-work24.ts`를 따른다. 주소는 `https://www.work24.go.kr/cm/openApi/call/wk/` + 서비스, `authKey` 쿼리를 쓴다.
    - 215L01: `returnType=JSON&jobCont=<띄어쓰기 뺀 낱말>&limit=10`
    - 212D01: `returnType=XML&target=JOBDTL&jobGb=1&jobCd=<코드>&dtlGb=1`
    - 21L01: `returnType=XML&target=CMCD&dtlGb=<n>`
- 대체 자료 규칙:
  - 키가 없으면 그 출처만 대체 자료를 쓴다.
  - 키가 있는데 호출이 실패하면 **그 요청은 503 `unavailable`**이다(§9-5 "실제 API 오류"). 조용히 모의로 바꾸면 실제인 줄 알고 검수하게 된다.
  - 시험·빌드는 실제 API를 부르지 않는다(httpx `MockTransport`). 실제 호출 시험은 키가 있을 때만 돈다.
- 카드 규칙(§2 ⓪, §9-5):
  - 능력단위 1개가 후보 1개다.
  - 수준이 `HIGH_LEVEL_MIN = 6` 이상이면 `high_level: true`로 표시만 하고 빼지 않는다. 수준을 모르면 표시하지 않는다.
  - LLM은 `kind: task` 카드만 쓴다.
  - 카드 ID는 코드가 정한다: `job` 앞 두 글자 대문자 + 두 자리 번호(`frontend` → `FR01`).
  - 앞에서부터 12개는 `core: true`다.
  - `mapping_confidence`는 늘 `"draft"`다.
  - `ncs`는 `[{subcategory, unit, ablt_unit}]`로 묶음 근거를 남긴다.
- 시간:
  - 엔드포인트 `CARDS_DEADLINE_S = 55.0`, LLM 한 번 `min(45.0, 남은 시간)`
  - 다시 쓰기는 남은 시간이 `CARDS_REWRITE_MIN_LEFT_S = 20.0` 이상일 때만 한다.
  - CLI는 `--deadline`(기본 180초)으로 늘린다.
- LLM 역할은 `"accurate"`다(§4).
- 로그 한 줄. 카드 글은 없다.
  - 성공: `[ai] cards job=frontend candidates=34 cards=15 issues=2 retried=1 sources=ncs_gw:mock,duty:snapshot,job:snapshot,codes:snapshot ms=… model=…`
  - 503: `[ai] cards unavailable code=… ms=…`

## Review Focus

1. 키가 있는데 실제 API가 실패하면 모의로 조용히 바뀌지 않고 503이 된다 — Task 1 `test_key_present_failure_raises`, Task 3 `test_real_source_error_503`.
2. LLM이 후보에 없는 능력단위 코드를 묶거나 같은 능력단위를 두 카드에 묶으면 그 카드만 걸린다 — Task 2 `test_unit_not_in_candidates`, `test_unit_reused_across_cards`.
3. 질문 틀에 "공고"가 있거나 4유형(conflict·opportunity·depth·explore) 중 하나가 빠지면 걸린다(화면에 검수 문장으로 나가는 글) — Task 2 `test_question_mentions_posting`, `test_missing_question_type`.
4. `max_cards`보다 많이 쓰면 앞에서 잘리고 `too_many_cards` 문제가 남는다. 잘린 카드의 능력단위는 `used_in: null`이 된다 — Task 3 `test_truncates_to_max_cards`.
5. 응답 `meta.sources`가 출처마다 실제·스냅숏·모의를 정확히 말한다(모의를 실제로 보이지 않게) — Task 3 `test_meta_sources_mock_and_snapshot`.

### Task 3: ⓪ 그래프와 `POST /api/ai/v1/card-drafts`

**Files:**
- Create: `api/_agent/graphs/cards.py`, `api/_agent/prompts/cards.py`
- Modify: `api/_agent/schemas.py`, `api/_agent/budget.py`(Global Constraints 시간 값), `api/_agent/app.py`
- Test: `api/_agent/tests/test_cards.py`

**Interfaces:**
- Consumes: Task 1 `CardSources`·`SourceError`, Task 2 `build_candidates`·`check_card_draft`, 1단계 `call_with_deadline`·`FakeLlm`·`LlmError`, `prompts/common.py`
- Produces `schemas.py`(명세 4번과 같은 이름):
  - `CardDraftRequest(job: str (^[a-z]+$), job_label: str (1~40자), ncs_subcategories: list[str] (1~5개, 각 ^\d{8}$), job_dictionary_code: str | None = None, max_cards: int = 15 (1~30))`
  - `CandidateOut(ablt_unit, unit, subcategory, level: int | None, high_level: bool, used_in: str | None)`
  - `CardDraft`: `CardDef` 모양 — `id, kind: Literal["task"], core, label, plain, examples, ncs: list[{subcategory, unit, ablt_unit}], job_dictionary: str | None, mapping_confidence: Literal["draft"], posting_signals, questions, example_question: str | None, interpretation`
  - `CardIssue(card_id: str | None, rule: str)`
  - `CardDraftMeta(graph_version: "cards-1", model, created_at, sources: dict[str, Literal["실제","실제 스냅숏","모의"]])`
  - `CardDraftResponse(candidates, cards, issues, meta)`
- Produces `graphs/cards.py`: `class CardsAgent(llm, root: Path, env: Mapping, http=None, clock=time.monotonic, now=…, deadline_s: float = CARDS_DEADLINE_S)`(한 번 compile), `async run(req) -> CardDraftResponse`
  - 노드는 §9-5와 같다: `fetch`(세분류마다 `units`, 직업사전 `duties` → 띄어쓰기 뺀 낱말마다 `recommend`, `job_code`) → `candidates` → `group_and_write` → `check` → `rewrite_cards`(걸린 카드만, 한 번, 남은 시간 문턱) → `finish`
  - `SourceError`이면 503이다. 후보가 0개이면 400 `invalid_request`(`"no units"`)이다.
  - LLM 출력: `{"cards":[{label, plain, examples, units:[ablt_unit…], posting_signals, questions, example_question, interpretation}]}`. ID·`kind`·`core`·`ncs`·`mapping_confidence`·`job_dictionary`는 코드가 채운다.
  - 다시 쓰기에서도 걸린 카드는 응답에 남기고 `issues`에 적는다. 사람이 검수할 때 본다.
  - `max_cards`를 넘으면 앞에서 자르고 `CardIssue(None, "too_many_cards")`를 남긴다.
  - `finish`가 `candidates[].used_in`을 채운다.
- Produces `prompts/cards.py`: `SYSTEM`, `user_message(req, candidates, duties, example_card, only=None, issues=None)`
  - 예시 카드 하나로 `cards.backend.json` BE01을 보낸다. 글 모양 예시이며, 능력단위 근거는 아니다.
  - SYSTEM 원칙:
    - 후보를 업무 단위로 묶는다(`max_cards` 이하, 한 능력단위는 한 카드에만).
    - 카드 이름은 구직자가 아는 말로 쓴다.
    - `plain`·`examples`는 해요체다.
    - 질문 틀은 "…습니다/…인가요?"이고 4유형 모두 쓴다. `opportunity`·`depth`는 `{anchor}`로 시작해도 된다.
    - 질문 틀에 "공고"를 쓰지 않는다.
    - `high_level` 후보는 신입과 먼 일이라고 `plain`에 드러낸다.
