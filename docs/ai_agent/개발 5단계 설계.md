# 개발 5단계 설계 — ④ 평가와 ② 질문 맞춤화

> 2026-10-30 AI 담당과 브레인스토밍으로 정함. 「에이전트 설계 확정」 §2 ④·D-313을 이 문서가 넓힌다. 겹치면 이 문서를 따른다. 구현 계획은 이 문서를 바탕으로 `개발 5단계 계획.md`에 쓴다.
> 표시: **[AI 담당]** 대화에서 AI 담당이 정한 것 · **[Claude]** 대화에서 Claude가 제안하고 AI 담당이 반대하지 않은 것 · **[구현자]** 구현자가 정해도 되는 것.

에이전트 번호(개발 단계 번호와 다르다):

| 기호 | 에이전트 | 결과가 가는 곳 | 5단계 평가 무게 |
|---|---|---|---|
| ⓪ | 업무 카드 초안 | 사람 검수 뒤 `data/cards.*.json` | 가볍게(자동 지표 3개) |
| ① | 공고 분석 | 화면(형광펜·확인할 점) | **꼼꼼히** |
| ② | 1차 질문 | 화면 | **꼼꼼히** |
| ③ | 최종 판정·질문 | 화면 | **꼼꼼히** |
| ④ | 평가(이 문서) | 로컬 보고서 | — |

①②③은 검수 없이 사용자 화면에 바로 가므로 평가의 무게를 여기에 둔다. ⓪은 사람이 검수하는 초안이라 가볍게 잰다 [AI 담당].

## 1. 왜 하나

- AI가 낸 답의 품질을 숫자로 재는 틀이 없다. 4.5단계(실제 API 전환)에서 노드·자료가 더 붙을 수 있어서, 파이프라인이 바뀌어도 그대로 쓰는 평가가 필요하다.
- AI 담당이 직접 본 문제: ② 1차 질문이 너무 간단하다. "DB 테이블 설계는 백엔드 개발자가 직접 하나요, 별도 담당자가 있나요?"는 어느 회사에나 맞는다. **회사(공고)와 구직자 내용이 더 들어가야 한다** [AI 담당].
- 원인은 자료가 아니라 프롬프트다. ②는 이미 공고 전체를 받지만 `prompts/first.py`가 "template_text 뜻 지키기 · evidence.quote 외 인용 금지 · has_exp 문항만 구직자 메모"로 묶어 둔다. 구직자 정보는 경험 한 줄뿐이다.

그래서 5단계는 둘이다.
1. **④ 평가**: ①·②·③의 답 품질을 꼼꼼히 재는 로컬 평가. ⓪은 자동 지표 세 개로 가볍게.
2. **② 맞춤화**: 공고의 기술 스택·회사 정보와 이력서를 질문에 넣고, 평가로 전후를 잰다 [AI 담당].

## 2. 목표 · 비목표 · 실패

목표
- ① 카드 상태가 사람 정답과 얼마나 맞는지, 어떻게 틀리는지 안다.
- ②③ 질문이 "이 회사·이 구직자에게만 맞는지"를 숫자로 본다.
- ② 맞춤화 전후를 같은 자료로 비교해 나아졌는지 보인다.
- 4.5단계 뒤 파이프라인 안쪽이 바뀌어도 평가 코드·정답표를 다시 만들지 않는다.

비목표
- 실행 중 LLM 판정(시간 예산 때문에 실행 중은 규칙만, D-306 그대로).
- 질문 순서·카드 고르기 규칙(`shared/`) 바꾸기.
- 가짜 응답 모드(`build:mock`, 브라우저 안 생성)에 이력서 쓰기.
- 회사 신호를 ② 질문에 넣기. 신호 질문은 ①이 만들어 화면 신호 상자가 보인다(설계 확정 §7) [Claude].
- 평가를 CI·배포에 넣기. 로컬에서 사람이 돌린다.

실패(돌아가도 실패로 본다)
- 질문이 구체적이 되면서 공고·이력서에 없는 기술·사실을 지어낸다. 맞춤도가 올라도 안전 지표가 기준값보다 나빠지면 개선이 아니다.
- 실제 회사 공고 원문·공고 번호가 레포에 커밋된다.
- 이력서의 이름·나이·성별·주소·연락처·병역·학교 이름이 AI로 간다.
- 프롬프트를 평가용 30건을 보며 고쳐 점수가 저절로 오른다.
- 신입 대상 서비스인데 질문이 경력자용으로 어려워진다.

## 3. 제약

- 레포 규칙(CLAUDE.md): 실제 사람·회사 정보 커밋 금지, 키는 `process.env`/`os.environ`만, 경험 한 줄(이제 이력서 칸도)은 서버에서 저장·로그하지 않음, `e2e/`는 고치지 않고 `SPEC-ISSUES.md`에 적음, 화면 문구는 `ACCEPTANCE.md` 「정확한 문구」 그대로.
- 무엇을 물을지(카드·유형·순서)는 TS `shared/` 규칙만 정한다. Python은 문장·판정·분석만 한다(설계 확정 §1).
- 새 검사 규칙은 `shared/fixtures/validate-cases.json`에 예시부터 더하고 TS `validate.ts`와 Python `checks.py`가 같이 지킨다.
- 실행 중 시간 예산(②: 18초, 다시 쓰기는 남은 시간 8초 이상일 때만)은 그대로다. 프롬프트·입력이 길어져 p95가 예산을 넘으면 안 된다.
- 평가는 4.5단계가 끝난 최종 파이프라인으로 잰다(D-344).
- 판정용 LLM은 같은 `llm()`(엔노이아)을 쓴다. DeepEval 없음(D-313).

## 4. 평가 공통 구조 [Claude]

### 4-1. 계약만 본다

평가는 각 API의 **요청 → 응답 모양**(`docs/AI-API-명세서.md`)만 입력·출력으로 쓴다. 그래프 노드 이름·중간 상태는 보지 않는다. 4.5단계에서 노드가 늘거나 모델이 바뀌어도 평가 코드는 그대로다. 응답 모양이 바뀌면 그때만 고친다.

### 4-2. 자료와 결과의 자리

| 자리 | 내용 | git |
|---|---|---|
| `evals/` | 평가 코드(Python), 지표 정의, 판정 프롬프트, 가상 구직자 | 커밋 |
| `evals/data/` | 고용24 공고 스냅숏, 정답표 CSV, 정답 JSON | **git 밖**(`.gitignore`). 팀 공유는 드라이브 |
| `review/evals/<날짜>-<짧은 커밋>/` | 한 번 돌린 결과: 사례별 JSONL + `summary.md` | git 밖 |

- 실행 기록마다 커밋, 모델 이름(엔노이아 에이전트별), 프롬프트 지문(프롬프트 글의 해시), 정답표 지문, 돌린 시각을 `summary.md` 머리에 적는다.
- 두 실행을 나란히 놓는 비교 명령을 둔다(지표별 전·후·차이, 바뀐 사례 목록).
- 평가 실행에서도 공고 원문·질문 원문을 콘솔 로그에 찍지 않는다. 결과 파일에만 둔다.

### 4-3. 평가용 공고 30건 [AI 담당: 고용24 채용공고에서 30건 선별]

- 고른 날의 공고를 **스냅숏**으로 저장한다. 공고는 마감되면 사라지거나 바뀐다. 모양은 지금 `posting`과 같은 고용24 필드(`corpNm`·`jobCont`·`pfCond`·`sal` …)로 둔다.
- 4.5단계에서 고용24 응답 → `posting` 변환이 바뀌면 스냅숏을 다시 변환할 수 있게 **받은 원본도 같이** 둔다. 정답표는 공고 번호 × 카드로 묶여 있어 변환이 바뀌어도 다시 매기지 않는다(근거 칸 이름이 바뀌면 그 열만 옮김).
- 고르는 기준(미리 적어 두기) [Claude]: 백엔드 직무만(카드 사전이 백엔드 17장). 그 안에서 연봉이 적힌/안 적힌, 큰/작은 회사, SI·상주, 업무가 두루뭉술한 공고, 기술 스택이 자세한/거의 없는 공고가 섞이게. 같은 회사 공고는 한 건만.
- **30건은 재는 데만 쓴다.** 프롬프트는 시연 모의 공고 7건으로 고친다. 30건에서 예시를 꼭 가져오면 그 공고는 평가에서 빼고 다른 공고로 채운다.

### 4-4. 판정용 LLM을 믿을 수 있는지

- 판정 LLM(공고 맞히기, 경험 부풀리기, 전제)은 정확 모델 에이전트로 부른다 [구현자: 에이전트 ID 변수].
- 처음 한 번, 사람 점수 표본 20개에서 사람도 "근거 없는 전제"·"경험 부풀리기"를 예/아니오로 매겨, 판정 LLM과의 **판정-사람 일치율**을 낸다(안전 지표를 맡는 두 판정이라 믿을 수 있어야 한다). 낮으면 판정 프롬프트부터 고친다. 일치율은 `summary.md`에 늘 같이 적는다.

## 4-5. ⓪ 업무 카드 초안 평가 (가볍게) [AI 담당]

⓪은 초안 도구라 틀린 묶음은 사람 검수에서 걸러진다. 능력단위를 카드로 묶는 정답도 하나가 아니다. 그래서 정답 사전과 맞대는 지표(후보 재현율, 묶기 쌍 정밀도·재현율)는 **두지 않는다**. 이런 지표는 품질이 아니라 "기존 사전과 얼마나 닮았나"를 재고, 정답 사전이 백엔드 하나뿐이라 ⓪이 쓰일 새 직무에는 쓸 수 없다. 사람 점수와 공고 낱말 적중률도 두지 않는다.

정답 없이 어느 직무에나 자동으로 재는 지표 세 개만 둔다.

| 지표 | 재는 법 |
|---|---|
| 분야 밖 후보 | 후보 능력단위 코드 앞자리가 입력한 NCS 세분류와 다르면 분야 밖. 그 비율과, 분야 밖 후보가 카드에 묶이지 않고 "안 쓰인 후보"로 빠졌는지 |
| 공고 덮는 비율 | 그 직무 공고의 「담당업무」 줄마다 맞는 카드가 있는지(판정 LLM). 없는 줄 목록을 보고서에 적는다(사전에 빈 구멍). 백엔드는 4-3의 공고 30건을 쓰고 정답표는 필요 없다 |
| 흔들림 | 같은 입력을 두 번 돌려 능력단위 묶음이 얼마나 같은지(같은 카드에 묶인 쌍의 겹침) |

- 이미 만든 초안(`review/card-drafts/<직무>.json`)이 있으면 ⓪을 다시 부르지 않고 평가만 돈다. ⓪은 흔들림을 잴 때만 두 번 부른다.
- 평가는 `data/`를 읽기만 한다. 지금 보고서의 「기존 사전과 비교」 칸은 그대로 둔다.

## 5. ① 공고 분석 평가

### 5-1. 정답표 (스프레드시트) [AI 담당: 스프레드시트]

- 매기는 사람: 두 사람. 15건씩 나누고 5건은 둘 다 매긴다(D-313·파이프라인 문서 §4).
- 탭
  - `cards`: 한 줄 = 공고 × 카드(30 × 17 = 510줄). 칸: 공고 번호 · 카드 ID · 카드 이름 · 상태(드롭다운 `explicit`/`inferred`/`vague`/`absent`) · 근거 칸(드롭다운 8개, `explicit`·`vague`면 필수, `inferred`는 선택) · 메모 · 매긴 사람.
  - `blanks`: 한 줄 = 공고 × 처우 항목. 칸: 상태(`missing`/`vague`/`check`/적힘) · 근거 칸 · 메모 · 매긴 사람.
  - 겹치는 5건은 사람마다 탭을 따로(`cards_A`·`cards_B`) 두어 서로 보지 않는다.
- 처음 값은 비운다. `absent`를 미리 채우지 않고 ①의 결과도 보여 주지 않는다(따라 매기기 방지) [Claude].
- 근거는 인용 문장이 아니라 **칸 이름**만 적는다. 같은 근거라도 끊는 곳이 달라 글자 비교가 안 된다 [Claude].
- 매기기 전에 **기준표** 한 장: 카드마다 `explicit`/`inferred`/`vague`/`absent` 예시 문장 한두 개. 겹친 5건에서 어긋난 것을 이야기하고 기준표에 더한 뒤 나머지를 매긴다.

### 5-2. 시트 → 정답

1. CSV로 내려받아 `evals/data/`에 둔다.
2. 검사 명령: 빈 상태, `explicit`·`vague`인데 근거 칸 없음, 사전에 없는 카드 ID, 공고 번호가 스냅숏에 없음 → 줄 번호와 함께 멈춤.
3. 통과하면 정답 JSON으로 바꾼다. 겹친 5건은 이야기해서 맞춘 값을 정답으로 쓴다(어느 탭을 정답으로 쓸지 표시하는 칸 하나) [구현자: 모양].

### 5-3. 지표

| 지표 | 재는 법 | 목표 |
|---|---|---|
| 사람끼리 일치율 | 겹친 5건. 둘 다 `absent`인 칸은 빼고 일치율 + Cohen's kappa | 기준값(①의 목표가 됨) |
| 상태 정확도 | `absent` 뺀 정확도, 상태별 정밀도·재현율 | 사람끼리 일치율 근처 |
| 혼동표 | 정답 상태 × ① 상태 4×4 | 아래 무게로 읽음 |
| 지어낸 있음 | 정답 `absent` → ① `explicit`·`vague` 건수 | 0에 가깝게(가장 나쁜 틀림: 질문이 거짓 전제를 깐다) |
| 놓친 있음 | 정답 `explicit` → ① `absent` 건수 | 따로 봄 |
| 근거 실재율 | ① `evidence.quote`가 그 칸 원문에 글자 그대로 (코드) | 100% |
| 근거 칸 일치 | ① `evidence.field`가 정답 근거 칸과 같은지 | 따로 봄 |
| 처우 빈칸 정확도 | `blanks` 상태 비교 | 따로 봄 |
| 응답 시간 p95 | 호출마다 | 함수 한도 안 |

- 회사 신호는 정답표로 재지 않는다. 코드 규칙으로 켜지므로 단위 시험이 지킨다 [Claude].
- 걸러내기 **전** 위반율(D-313)은 ①에서는 재지 않는다. ①의 검사는 그래프 안쪽 노드라, 재려면 4-1 "계약만 본다"를 깨야 한다. ①은 최종 결과의 근거 실재율로 본다 [Claude, 계획 때 고침]. ②는 프롬프트 한 번 호출이라 6-2대로 잰다.

## 6. ②③ 질문 평가

### 6-1. 입력 만들기

- 공고 30건 × 가상 구직자 2명 = 60 사례.
  - 구직자 A: 지금 김00(`data/persona.json`).
  - 구직자 B: **새 가상 인물**. 김00과 기술이 겹치지 않게(예: Java·Spring 실무형 훈련, 결제·주문 쪽 프로젝트) [Claude]. 이름은 가상 규칙대로(`이00` 등), 연락처는 예시 값.
  - 구직자마다 기대·걱정 고르기와 경험 한 줄을 고정해 둔다(사례마다 같은 마음) [구현자: 고르기 값].
- ②③에 넣는 공고 분석은 **①이 이 30건에 낸 결과**를 쓴다(사용자가 실제로 받는 흐름 그대로). 처음에는 정답표 상태를 쓰려 했으나, 정답표에는 근거 칸 이름만 있고 인용 문장(`evidence.quote`)이 없어 ②가 인용할 재료가 없다. ①의 틀림은 5절에서 따로 재므로 섞여도 원인을 나눠 볼 수 있다. 이렇게 하면 ②③ 평가가 정답표 매기기를 기다리지 않는다 [Claude, 계획 때 고침].
- 카드 5개 고르기·유형·순서는 TS `shared/` 규칙으로 만든다. 평가가 따로 규칙을 만들지 않는다 [구현자: TS 스크립트로 요청 JSON을 만들어 Python이 읽든, 다른 길이든].
- 검수 문장 대체율은 **TS 최종 검사(`validate.ts`)를 거친 뒤** 결과로 잰다.

### 6-2. 지표

| 지표 | 재는 법 | 비교 |
|---|---|---|
| 공고 맞히기(회사 맞춤도) | 판정 LLM에 질문 하나 + 공고 3건(진짜 1 + 같은 백엔드 공고 2, 무작위·순서 섞음)을 주고 어느 공고 질문인지 고르게 함. 맞힌 비율 | 우연 33%. 기준값보다 올라야 함 |
| 구직자 맞춤도 | 같은 공고의 A·B 질문 세트가 얼마나 다른지 + 판정 LLM에 질문 하나와 A·B 이력서를 주고 누구 질문인지 고르게 함 | 우연 50%. 기준값보다 올라야 함 |
| 지어낸 사실 | 질문 속 기술·분야·경험이 공고 원문·보낸 이력서 칸에 없는 비율(규칙 + 판정 LLM) | 기준값보다 나빠지면 안 됨 |
| 근거 없는 전제 | `absent` 카드 질문이 공고에 있는 것처럼 말한 비율(판정 LLM) | 기준값보다 나빠지면 안 됨 |
| 경험 부풀리기 | 1인칭 경험이 경험 한 줄·보낸 이력서 칸에 없는 사실을 더했는지(판정 LLM) | 기준값보다 나빠지면 안 됨 |
| 걸러내기 전 위반율 | Python 검사를 끈 원문의 인용·전제·금지어·숫자·새 기술 낱말 위반 | 따로 봄 |
| 검수 문장 대체율 | TS 최종 결과의 `source: template` 비율 | 기준값보다 나빠지면 안 됨 |
| 응답 시간 p95 | ② 18초 · ③-1 8초 · ③-2 10초 안 | 예산 안 |
| 사람 점수 | 표본 20개(구직자 A·B 섞어)를 세 기준 1~3점: 면접에서 그대로 쓸 만한가 · 이 회사에만 맞는가 · 신입이 묻기에 자연스러운가 | 기준값보다 올라야 함 |

- "신입이 묻기에 자연스러운가"는 맞춤화가 질문을 경력자용으로 어렵게 만드는 쪽으로 가지 않게 잡는다 [Claude].
- LLM 답이 매번 달라서, 기준값과 개선 뒤 실행은 같은 사례를 **두 번** 돌려 차이 폭을 같이 적는다 [구현자: 횟수는 비용 보고 정함].

### 6-3. ③ 최종

- `final-judgements`는 정답이 있다(`confirmed`·`mismatch`·`still_unknown`). 정답표 시트에 `judgements` 탭을 더한다: 한 줄 = 공고 · 카드 · 1차 질문 · 사람이 쓴 "들은 답" · 정답 판정. 상태마다 10개씩, 30줄 [Claude]. 지표는 판정 정확도와 상태별 혼동표, `still_unknown`으로 빠진 비율.
- `final-questions`는 ②와 같은 맞춤도·안전 지표를 쓴다. 들은 답은 문장 호출에 보내지 않는 규칙(설계 확정 §2 ③)은 그대로다.

## 7. ② 질문 맞춤화

### 7-1. 공고 내용 넣기 [AI 담당]

- 카드·유형·`template_text`의 **묻는 것**은 그대로 지킨다. 그 틀 안에서 공고에 적힌 기술 스택·서비스 분야·회사 소개를 끌어와 이 회사에만 맞는 문장을 쓴다.
  - 예: "DB 테이블 설계는 백엔드 개발자가 직접 하나요?" → "공공·금융 시스템 프로젝트에서 DB 테이블 설계는 백엔드 개발자가 직접 하나요, 고객사나 별도 DA가 정해 주나요?"
- '…' 인용은 지금처럼 `evidence.quote`만. 공고의 다른 말은 인용부호 없이 풀어 쓴다(인용 검사 규칙 그대로).
- 숫자·회사 평가·처우 단정 금지는 그대로.
- "회사 정보"는 공고에 적힌 회사 소개·업종·규모·사업 내용(`busiCont`·`indTpNm`·`busiSize`·`jobCont` 회사소개)까지다. 회사 신호(국민연금·EIS 등)는 넣지 않는다.

### 7-2. 이력서 보내기 [AI 담당: 범위 승인]

- 보내는 칸(허용 목록): 희망 경력 구분 · 기술 목록 · 프로젝트(이름·스택·한 줄) · 직업훈련(이름·한 줄) · 자격증 이름.
- 보내지 않는 칸: 이름 · 성별 · 출생 연도 · 나이 · 주소 · 연락처 · 이메일 · 병역 · 학교 이름 · 자기소개서 · 그 밖의 모든 칸.
- 고르는 곳은 TS `shared/` 한 함수(허용 목록). 이력서에 칸이 새로 생겨도 저절로 나가지 않는다. 단위 시험으로 "허용 목록 밖 칸은 요청에 없음"을 고정한다.
- 이력서는 경험 한 줄과 같은 길로 간다: 화면이 허용 목록 칸만 `/api/questions` 요청에 싣고, TS 서버가 같은 허용 목록을 한 번 더 걸러 Python에 보낸다 [Claude]. 시연에서는 `persona.json`(이력서 화면과 같은 값), 실제 서비스에서는 고용24 이력서가 출처다.
- 이력서 칸은 경험 한 줄과 같이 다룬다: 서버에서 저장·로그하지 않는다. 프롬프트에서 `<구직자 이력>` 같은 자료 상자로 감싸 지시로 읽지 않게 한다.
- 요청 계약: `first-questions`에 선택 필드 하나(예: `resume`)를 더한다. 없으면 지금처럼 동작한다(뒤로 맞음). `final-questions`에도 쓸지는 [구현자: ② 결과를 보고, 쓰면 같은 허용 목록].
- **어느 문항에 이력서를 붙일지는 TS 규칙이 정한다**(무엇을 물을지는 TS만 — 설계 확정 §1). 지금 `has_exp`(경험 한 줄을 붙일 문항 하나)는 그대로 두고, 이력서 사실을 쓸 수 있는 문항을 표시하는 값을 문항마다 더한다 [구현자: 카드 ↔ 이력서 맞추는 규칙. 예: `experience_chips`의 `card_id`, 기술 낱말 겹침].
- 실행 중 검사 `has_exp: false` 문항의 1인칭 경험 탈락 규칙은 "이력서 표시도 없는 문항"으로 좁힌다. 근거가 있는지는 실행 중에 알 수 없으므로 평가의 경험 부풀리기로 잰다.

### 7-3. 새 검사: 지어낸 기술·분야 낱말

- 기술·분야 낱말 목록(예: Spring, JPA, Kafka, Redis, MSA, Kubernetes, SI, SM, 전자정부 표준프레임워크 …)을 자료 파일 하나로 둔다 [구현자: 자리·목록].
- 질문에 목록 낱말이 있는데 공고 원문에도, 보낸 이력서 칸에도 없으면 그 문항은 탈락 → 다시 쓰기(시간 있으면) → 검수 문장.
- 대소문자·띄어쓰기·한영 표기(스프링/Spring)는 같은 낱말로 본다.
- `validate-cases.json`에 예시부터 더하고 TS·Python이 같이 돌린다.

### 7-4. 같이 고칠 글

- `docs/AI-API-명세서.md` 1번 요청 필드, `docs/API-SPEC.md`.
- /about-ai 개인정보 "실제 서비스에서 AI로 넘기는 것은 …" 줄(`src/pages/AboutAiPage.vue`, D-286)에 이력서 칸을 더한다. 화면 문구는 `ACCEPTANCE.md` 「정확한 문구」를 먼저 바꿔야 하고 시험이 이 글을 찾을 수 있다. **바꾸기 전에 세진 승인**(REVIEW-HOLD에 올림), e2e가 걸리면 `SPEC-ISSUES.md`에 적는다.
- 경험 한 줄 안내(`EXPERIENCE_PRIVACY`)는 이력서가 같이 간다는 말이 필요한지 같이 본다.
- 가짜 응답 모드 안내("고른 것과 적은 글이 이 브라우저 밖으로 나가지 않아요")는 그대로 맞다(가짜 응답 모드는 이력서를 쓰지 않음).

## 8. 순서

0. 4.5단계(실제 API 전환)는 staging에 합쳐졌다(PR #5). 시연 7건 카드 판정 검수·적용은 프롬프트를 고칠 기준 자료라 5단계 5번 전에 끝낸다.
1. **사람 일**(2와 같이 감): 공고 30건 고르기 → 기준표 → 겹친 5건 매기기·맞추기 → 나머지 25건 → `judgements` 30줄 쓰기.
2. `evals/` 뼈대: 실행 기록·비교 명령, 시트 검사·변환, ① 지표. ⓪ 지표 세 개(4-5)도 여기서 같이 만든다(공고 덮는 비율은 공고 30건이 모인 뒤).
3. ②③ 입력 만들기(TS 규칙), 판정 LLM 지표, 판정-사람 일치 확인.
4. **기준값**: 지금 ②③으로 전 지표를 두 번 잰다.
5. ② 공고 내용 넣기(7-1) + 기술 낱말 검사(7-3) → 다시 잼.
6. 이력서 보내기(7-2) → 다시 잼. 5와 6을 따로 재서 어느 쪽이 얼마나 도왔는지 나눈다 [Claude].
7. 7-4 글 고치기(승인 받은 뒤), 5단계 보고서(기준값 → 5 → 6 비교표).

## 9. 구현자에게 남긴 것

- `evals/` 안 파일 나누기, 명령 이름(`npm run eval:*` 등), 결과 JSONL 모양.
- 공고 30건을 받는 길: 고용24 채용정보 키가 있으면 공고 번호 목록으로 받아 스냅숏을 만드는 스크립트, 없으면 사람이 붙여 넣는 양식. 어느 쪽이든 받은 원본과 변환본을 `evals/data/`에 둔다.
- 처우 항목 목록은 `data/offer-blanks.json`을 따른다.
- TS 규칙으로 요청을 만드는 길(스크립트·서버 등). 서버를 띄우면 명령이 끝날 때 끈다(CLAUDE.md).
- 판정 프롬프트 글, 엔노이아 동시 호출 수(비용·속도 제한 보고).
- 구직자 B의 구체 내용, 고르기 값.
- 기술 낱말 목록의 처음 내용과 자리.
- 카드 ↔ 이력서 맞추는 TS 규칙.
- 노드별 추적(LangSmith 등)은 기본으로 끔. 켜면 실제 회사 공고가 외부로 나가므로 켜는 사람이 정한다.
